A Session is always in one of four states. Asleep Sessions cost nothing but disk, so a Runner can hold many more Sessions than it runs at once.

<LifecycleDiagram />

| State        | Sandbox                                           | Claude Code           | Prompts                                |
| ------------ | ------------------------------------------------- | --------------------- | -------------------------------------- |
| **Active**   | Running                                           | Running               | Delivered in order, one Turn at a time |
| **Asleep**   | Stopped, disks kept                               | Stopped               | The Creator's next one wakes it        |
| **Frozen**   | As the Runner left it                             | As the Runner left it | Wait until the Runner is back          |
| **Archived** | Destroyed; Workspace and Claude Code's state kept | Stopped               | Refused                                |

## Going to sleep

The Hub puts an Active Session to sleep after 15 minutes ([`HUB_SLEEP_AFTER_MS`](/reference/configuration/#hub)) with none of these:

- a Turn or [subagent](/guides/work-with-subagents/) running, or a prompt queued;
- a Participant present;
- a [`kndl forward`](/guides/forward-a-sessions-ports/) connected;
- **Keep awake** on.

**Sleep now** in the Session's header puts it to sleep at once. A Runner also puts its Sessions to sleep before it updates, once their running Turns end.

Asleep, the Sandbox is stopped and its disks are kept. Docker's containers are stopped first, so databases shut down cleanly.

### Put to sleep, saying why

The Hub also puts a Session to sleep, even mid-Turn, when the token it runs on goes away. The Session's history says why:

- its Creator removed or replaced their Claude credential;
- its Creator was removed as a Member;
- its Creator has no Claude credential, as the Hub starts.

It can't wake until its Creator has a Claude credential again. A removed Member's Sessions stay readable until they're purged.

### Keep awake

**Keep awake** in a Session's header stops it going to sleep when idle. Use it for work that runs with nobody watching, such as a dev server or a long background command. Open ports and background commands don't keep a Session awake on their own ([ADR 0016](/contributing/decisions/0016-forwarding-a-sessions-ports/)).

- Only the Session's Creator can turn it on or off. The header, the sidebar and the Runners page show who turned it on.
- Turning it on wakes an Asleep Session.
- It stays on until the Creator turns it off, presses **Sleep now** or deletes the Session. A restore doesn't turn it back on.
- After a Runner update or restart, the Hub wakes the Session again.

## Waking

The Creator wakes an Asleep Session with a prompt, **Wake now** or a `kndl forward` of it. Anyone else's forward of an Asleep Session is told it's Asleep and that only its Creator can wake it. The Runner fetches the Creator's setup token from the Hub and starts the same Sandbox, with its dependencies, caches and Docker data as they were. Claude Code resumes the conversation.

A Session whose Creator has no Claude credential doesn't wake. A replaced token reaches the Session at its next wake.

- **A newer Environment version** makes the Sandbox afresh from its Build at the next wake, on the same Workspace and disks. **Restart** on the **Environment changed** banner does that at once.
- **A Runner behind the Hub** wakes no Session. Prompts wait until the Runner runs the Hub's commit.
- **Subagents** stop with their Session and are marked Interrupted. A message to one resumes it.

## When a start fails

If Claude Code can't start, the Session is Asleep, with the reason in its history. Queued prompts stay queued, and nothing retries on its own: the next prompt or **Wake now** tries again. See [Claude Code exited with code N](/troubleshooting/sessions/#claude-code-exited).

## Frozen

While its Runner is offline, a Session is Frozen. You can still read it, and prompts wait in its queue. Its Sandbox and Workspace are on that Runner, so it waits for it rather than moving.

Claude Code runs in the Sandbox, not in the Runner, so it keeps running while the Runner's connection is down or the Runner restarts. When the Runner is back, the Session is Active if Claude Code is still running, and Asleep otherwise.

## Deleting and restoring

The Session's Creator can delete it with the bin in its header. Deleting archives it at once: the Sandbox and its disks are destroyed, and the Workspace and Claude Code's state are kept. Everyone with access to the Repo can still read it.

- **Undo** on the toast restores it.
- **Archived Sessions** in the sidebar lists each Repo's Archived Sessions, with who deleted each and when. The Creator restores one with **Restore**.

A restored Session is Asleep, and the Creator's next prompt wakes it in a new Sandbox. The conversation carries on. Dependencies and Docker's data went with the old disks, so the Start script or Claude reinstalls them.

## Purging

30 days after it was archived ([`HUB_ARCHIVE_RETENTION_MS`](/reference/configuration/#hub)), the Hub purges a Session: its history, its queue, and on its Runner, its Workspace and disks. Work the Session never pushed is gone with it.

To free a Runner's disk sooner, anyone with access to the Repo can purge an Archived Session by hand, not just its Creator ([ADR 0027](/contributing/decisions/0027-anyone-who-sees-an-archived-session-can-purge-it/)). In **Archived Sessions**, press **Purge** on one, or tick several and press **Purge selected**, then confirm. A purged Session can't be restored. If its Runner is offline, the Session is gone from the Hub at once, and its Runner frees the disk when it reconnects.

## History

Every start, sleep, wake, delete, restore and failure is in the Session's history, with who did it.
